# Native cable section control

## Version 0.13.0: section metadata and worksheet verification

`get_cable_sections` now includes `loom_id`, `box_id` and `tape` for each section, and protects the corresponding run fields (including TapeColorCode) in its fingerprint. `set_cable_sections` accepts those three text fields as well as the existing name/slack/swag fields. Empty text clears metadata; values are limited to128 characters. Obtain a fresh fingerprint after this upgrade.

Metadata mutations are limited to exactly one section and zero breaks. In that verified case, the native SetCableSectionData selectors `Loom ID`, `Box ID` and `Tape` also update the run's Loom_ID, Box_ID and TapeColorCode. The second-event verifier checks both section values and this synchronization, while preserving scoped geometry, other identity/endpoint fields, topology and untouched section data. Mixed edits are fully preflighted. A matching section value with a different run value is not accepted as a no-op. Multi-section synchronization is unverified and rejected for metadata edits.

These selectors are missing from the short scripting function description but correspond to the editable section selectors in the [official 2026 worksheet function reference](https://github.com/Vectorworks/developer-worksheets/blob/main/Worksheet%20Functions/Vectorworks%202026%20US.md#specialized-for-cable). They were tested directly in the installed application before exposing them. Native worksheet formulas such as `=OBJECTDATA('cable section','Loom ID',1)` and `=LENGTH('cable section','Length',1)` were verified in the QA worksheet `VM QA Cable Native Data Comparison`. In this inch document, these worksheet length functions return feet while section API getters return millimetres; do not reuse one conversion for both routes.

Evidence: `native-section-loom-probe.json` and `cable-section-metadata-installed.json` under evidence/live-qa. The installed typed tool passed write/read/worksheet/stale-data/restore checks on both the API probe and the user's native-drawn cable. Eight typed calls, two worksheet scripts and four automatic verification events;37entertainment/287totaltools,156offline tests. Deployment `deployment-20260913-191622` has eight matching file hashes. Final worksheet recalculation confirmed all temporary metadata cleared, and QA was saved (`cable-sections-013-final.json`). The live worksheet remains in QA. This does not complete cable insertion, breaks, connections, or engineering verification.

## Earlier section length implementation

Version0.11.0 adds `get_cable_sections(object_ids)` and `set_cable_sections(expected_document, object_id, expected_fingerprint, sections)`. These use actual Vectorworks cable APIs, rather than private records or simulated Object Info button events. The reader returns native ordered part labels, section dimensions, break names/counts and a scoped state fingerprint. Supply that fingerprint to change existing section names, start/end slack and swag. Indices are1-based; index0 in GetCablePartsCnt requests the whole cable.

The installed SDK completion stub omitted seven functions that exist in the running VW2026. Current primary references are saved in `../vectorworks-research/cable-api-reference`; signature/source additions live in `tools/vs_supplement.json` and are merged by the index builder. The index now contains3078functions. [Official SetCableSectionData reference](https://github.com/Vectorworks/developer-scripting/blob/main/Function%20Reference/Functions/SetCableSectionData.md) identifies the editable selectors; Parts Ordered, Length and Total Vertical Drop are read-only.

**Units are asymmetric.** In the inch QA drawing, native section Length6096 equals the240inch route. Getters returned millimetres. A bare setter string `300` produced7620mm (300in), while `300mm` produced300mm. The wrapper therefore accepts explicit numeric `start_slack_mm`, `end_slack_mm`, `swag_mm` values and always adds the `mm` suffix. It rejects booleans, NaN/infinity, negative lengths and values over10000000mm. Never feed a getter's raw numeric string into a setter without a suffix.

Each setter preflights the entire requested edit list and current cable fingerprint. Native changes are followed by a separate read event through `get_cable_section_verification`; the fresh MCP server performs this automatically. Older clients must follow `requires_verification` and `next_command`, using `expected_document` and the returned `receipt`. A pending/failed read is not an invitation to resubmit the mutation. Failure retains per-field attempts and recovery information. No automatic rollback or private endpoint edit occurs.

Verification checks section names/dimensions, section count, break names and scoped preservation data (path control fingerprint, layer/class/style and selected ID/endpoint fields). Native stock changes are allowed and reported. This is not a full electrical graph or geometry-transform proof. Section loom data, connector assignment, stock compatibility and engineering suitability remain separate checks. Parts labels are not resource UUIDs. The reader requires a modern initialized CableObject, readable path geometry, at most100sections/100breaks/500parts per cable, and1..10cables per request. Setter edits at most25existing sections of one cable.

Live evidence: `evidence/live-qa/cable-section-native-roundtrip.json`. Six MCP calls plus two automatic verification events verified one section and zero breaks in the Toolkit QA file. Start slack8000mm, end slack200mm and swag100mm produced14396mm needed length; native stock rebuilt to50ft/15240mm. Restoring150mm start/end slack, zero swag and the original name restored the entire returned snapshot, including25ft ordered stock. Wrong/stale data is rejected. Multi-section editing, nonzero break enumeration, break insertion/removal and section loom synchronization have not yet been live-tested.

`SetCableBreakData` is now documented in the signature index, but no production break mutation tool is advertised. Its documented writable selector is only Name. Native use of the custom TRUE1/adapter parts, source connections, route associations/following and complete rigging workflows still need validation.
